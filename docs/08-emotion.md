# 08. 感情をキャラクターに映す

回答の感情を読み取り、**キャラクターの表情**と **VOICEVOX の声色**に映す。

いまの画面は文字と状態しか出していない。喋る相手が居るように見せたい、
というのがこの章の動機。

---

## 1. どこで感情を決めるか ★ 最初に決めること

回答を書いている**クラウド AI に、本文と一緒にタグを吐かせる。**

```
[happy] やったのだ！うまくいったのだ。
[neutral] 次は保存の仕組みを作るのだ。
```

### なぜこれか

| | |
|---|---|
| **追加の待ちがゼロ** | タグは文の**先頭**に来る。文が確定した時点でもう手元にあり、`/api/tts` を呼ぶ直前に間に合う |
| **課金がほぼゼロ** | 出力トークンが1文あたり 3〜5 個増えるだけ。**呼び出しの回数は増えない** |
| **既存の配管に乗る** | `sse.ts` が delta を正規化し、`speech/sentences.ts` が文に切る流れが既にある。文の切れ目＝感情の切り替え点なので、表情と声が文単位で揃う |

### 採らなかった案

| 案 | 理由 |
|---|---|
| **感情判定用にもう1回 AI を呼ぶ** | 入力トークンを2倍払い、待ちも増える。**一番筋が悪い** |
| **Apple の on-device AI**（Foundation Models） | 下に別記 |
| **辞書・規則だけ** | 却下ではなく**土台として使う**（3章）。ただしこれだけだと「文面は穏やかだが内容は謝罪」のような区別が付かない |
| 回答全体に1つのタグ | 長い回答で表情が固まる。文ごとに変わるのが自然 |

### Apple の on-device AI を調べた記録

「コマンドで使える Apple の AI」は公式 CLI ではなく **Foundation Models
framework**（macOS 26〜）。30 行ほどの Swift で CLI になる。実際に書いて確かめた。

```
macOS 26.6.2 / Xcode 26.6 / Apple M1
/System/Library/Frameworks/FoundationModels.framework      ある
swiftc -O -parse-as-library emotion.swift -o emotion       通る
./emotion "やったー！できたよ"  →  apple intelligence unavailable (exit 2)
```

- `@Generable` / `@Guide(.anyOf([...]))` の構造化出力はコンパイルが通る。
  API としては確実に `{label, intensity}` を取れる
- この機械では **Apple Intelligence が無効**（`appleIntelligenceNotEnabled`）。
  システム設定で有効にしてモデルを落とせば動く

**それでも採らない。** サーバーが Mac に据え置きになったので「Pi で動かない」は
問題にならなくなったが、**読み上げの直列パスに推論が1回挟まる**のが残る。
感情は「文が確定してから TTS を呼ぶまで」の間に要るので、1文ごとに待ちが乗る。
無料・オフラインと引き換えに**声が遅れる**のは、この機械では割に合わない。

> 常駐プロセスを立てて待ちを詰められれば、選択肢に戻る余地はある。
> `server/src/ai/types.ts` の `onDevice` を削った理由も、いまは
> 「Pi が最終的な置き場所だから」ではなくなっている。

## 2. タグの形式

**`[語]` を文の先頭に置く。** 語は下の5つに固定する。

```
[neutral] [happy] [sad] [angry] [surprised]
```

| 決めごと | 理由 |
|---|---|
| **半角の `[` `]`** | 全角より本文に紛れにくい。日本語の回答に `[` はまず出ない |
| **英語の小文字** | 表記ゆれが起きにくい。日本語（`[うれしい]`）は活用と漢字で揺れる |
| **文の先頭にだけ** | 到着が本文より早い、という性質がここから来る |
| **語は列挙して固定** | 「感情を書け」だと自由に作る（後述） |

### 採らなかった形式

| 形式 | 理由 |
|---|---|
| `happy: 本文` | コロンは本文にも出る。剥がし間違いが起きる |
| `<happy>本文</happy>` | 閉じタグの分だけトークンが増え、閉じ忘れの失敗が増える |
| JSON / structured output | 逐次配信と両立しない。**全部書き終わるまで喋れなくなる**ので論外 |
| tool use で別に返させる | 呼び出しが増える。逐次性も失う |

## 3. タグ付けが安定しない前提で作る ★ この章の本題

**モデルは指示どおりに書かないことがある。** 前提にして設計する。

### 原則: タグの有無に本文が依存しない

タグが1つも付かなくても、**回答は完全に成立する**こと。
感情は「付いていたら使う」上乗せであって、必須の情報にしない。

### 二段構え + 保険

```
タグが付いている  →  そのタグを使う
タグが無い        →  辞書で推定する（「！」→ happy、「ごめん」→ sad …）
どちらも当たらない →  neutral
```

**辞書を先に作る。** 課金ゼロ・遅延ゼロで確実に動き、表情と声色の配管を
先に通せる。タグはそのあとに足して**上書きする**形にする。

> **これが不安への一番の答え。** 配管（表情・声色・剥がし器）は辞書だけの
> 段階で完成しているので、**タグの付きが悪くても投資は無駄にならない。**
> 「不安だから入れない」ではなく「入れて、駄目なら切る」にできる。

### 失敗の種類と受け止め方

| 起きること | 見え方 | 受け止め方 |
|---|---|---|
| タグを付け忘れる | 表情が変わらない | 辞書に落ちる。**本文は無傷** |
| 知らない語を作る（`[excited]` `[うれしい]`） | 同上 | 表に無い語は捨てる。**捨てた語をログに出す**（表に足す材料になる） |
| **タグが delta の境界で割れる**（`[hap` / `py]`） | **タグを読み上げる** ★最悪 | 剥がす側で保留する（下記） |
| 文の途中にタグを入れる | 同上 | 剥がすだけ剥がし、**感情としては採らない** |
| **`[` で始まる本文**（`[1] のように…`） | **本文が消える** | **既知の語に完全一致したときだけ剥がす** |
| 全部同じタグになる | キャラが動かない | 実測しないと分からない。プロンプトで直す |
| 文体が硬くなる | 回答が不自然 | 同上。効かないならタグを切る |
| 途中で打ち切られる（`truncated`） | 閉じないタグ | 終端で保留分を本文に流す |

### 剥がし器の規則

`[` を見たら**そこから先を保留し、本文に流さない。**

1. 保留中に `]` が来た → 中身が**既知の語に完全一致**すれば感情として採り、捨てる。
   一致しなければ**保留分をそのまま本文に流す**
2. 保留が **12 文字**を超えた → 諦めて本文に流す。閉じないタグで永久に黙るのを防ぐ
3. ストリームの終端では、保留分を必ず流す

これで**タグを読み上げる事故は原理的に起きない。** 保留による遅れは
文頭の十数文字ぶんだけで、`]` は同じ delta か次の delta で来る。

`[1]` や `[注]` が消えないのは 1 の「完全一致」による。ここが決定的で、
「`[` で始まったら剥がす」にすると本文を壊す。

### 文の切れ目とタグの切れ目がずれる場合

`SentenceSplitter` は短い断片を次の文とまとめる（`MIN_LENGTH` = 8）。
そのため「はい。[happy] やったのだ！」が1文にまとまり、**タグが文の途中に来る**。

規則: **バッファが空のときに来たタグはいまの文に、そうでなければ次の文に効かせる。**

### 何を課金ゼロで確かめられるか ★

`../aichat/CLAUDE.md` と同じく、**本物の AI を呼んで動作確認はしない。**
確かめられる範囲を分けておく。

| | 課金 | 確かめ方 |
|---|---|---|
| **剥がし器** | **ゼロ** | テストで固める。delta を**1文字ずつ**流す・タグの真ん中で切る・`[1]` を混ぜる・閉じないタグ・終端での取りこぼし |
| **表情と声色の切り替わり** | **ゼロ** | stub に `?scenario=emotion` を足し、5種類のタグを含む固定応答を返す。**目で見て耳で聞いて**確かめられる |
| **辞書の当たり方** | **ゼロ** | テスト |
| **モデルが本当にタグを付けるか** | **あり** | ここだけは実測が要る。ユーザーが判断して測る |

最後の1つのために、計測できる形にしておく。

- サーバーのログに、**1文ごとに「タグの有無・語・捨てた語」を出す**
- `/admin` で**感情タグを切れる**ようにする。切っても本文は変わらない

### プロンプトの書き方

安定に効くのはここ。**サーバーが必ず足す部分**に置き、`/admin` の
`systemPrompt`（利用者が書き換える）とは分ける。**書き換えでタグの指示が
消えると、原因の分からない不調になる。**

- 語を**そのまま5つ列挙する**（「感情を書け」にしない）
- 「各文の**先頭**に必ず1つ」「タグ以外の説明をしない」
- **例を2つ**入れる
- 「迷ったら `[neutral]`」— 迷ったときの逃げ道を与えると、変な語を作りにくい

**Claude と Gemini で差が出る。** 両方に対応しているので、片方の付きが悪ければ
もう片方を使う手も残る。これも実測。

## 4. 感情の種類と対応表

**5つ。** 表情の絵と声色の両方を用意する必要があるので、まずここに絞る。

| タグ | 表情 | 声（ずんだもん） | 備考 |
|---|---|---|---|
| `neutral` | ふつう | 3 ノーマル | 既定。迷ったらここ |
| `happy` | わらう | 1 あまあま | |
| `sad` | しょんぼり | 76 なみだめ | |
| `angry` | ぷんぷん | 7 ツンツン | |
| `surprised` | びっくり | **3 ノーマル** | **対応する声が無い** |

★ **表情と声色は別の表にする。** 1対1に縛ると、声の無い感情を作れない。

### 話者を変えると声の表が変わる

ずんだもんは 8 スタイル（ノーマル / あまあま / ツンツン / セクシー / ささやき /
ヒソヒソ / ヘロヘロ / なみだめ）あるが、**話者ごとに構成が違う**。
四国めたんには「なみだめ」も「ヘロヘロ」も無い。

規則: **対応表を持たない話者では、声色を変えず表情だけ動かす。** 安全側に倒す。

### 声色を変えることの危険

同じチャットの中で声色が変わると、**「別人になった」と受け取られる**可能性がある。
実際に聞かないと分からないので、**表情と声色は `/admin` で別々に切れるようにする。**
まず表情だけで始めるのが安全。

## 5. どこで剥がすか

**サーバー。`ai/chat.ts` の正規化の中。** 経路が2つあるので、一箇所で済ませる。

```
上流の SSE ─▶ normalizeStream ─▶ [ タグ剥がし ] ─▶ event: delta   （本文。タグは入らない）
                                                └▶ event: emotion（感情。delta の直前）
```

正規化後の SSE に**タグが混ざらない**ので、下流（ブラウザ・`ws/session.ts`）は
`emotion` イベントを見るだけでよい。**剥がし忘れの経路が存在しなくなる。**

### API

`/api/chat`（SSE）にイベントを1つ足す。**順序が保証されるので位置の情報は要らない。**

```
event: emotion
data: {"label":"happy"}
```

WebSocket（`ws/protocol.ts`）は、**音声に添える**形にする。

```ts
| { type: "audio"; bytes: number; emotion: EmotionLabel }
```

### 表情を切り替えるのは「文字が出た瞬間」か「声が鳴り始めた瞬間」か ★

**声に合わせる。** キャラが喋っているように見せるのが目的なので、
口と表情が食い違うほうが不自然。

合成は先読みしているので、**文字は声より先に出る**（`speech/queue.ts`）。
だから `emotion` イベントをそのまま表情に反映させると**表情だけ先に動く。**
音声に添えて送り、鳴らす直前に切り替える。

### 触るところ

| ファイル | 変更 |
|---|---|
| `ai/emotion.ts`（新規） | タグ剥がし器・語の表・辞書 |
| `ai/chat.ts` | 正規化の後段に剥がし器を挟む |
| `ai/types.ts` | `EmotionLabel`・設定（下記）・感情ごとの話者 ID |
| `speech/tts.ts` | `synthesize` が話者の上書きを受ける |
| `speech/queue.ts` | `enqueue(text, emotion)`。`send` にも渡す |
| `ws/session.ts` | `emotion` を受けて `enqueue` に渡す |
| `ws/protocol.ts` | `audio` に `emotion` |
| `web/src/main.ts` | 表情の切り替え（音声の再生に合わせる） |
| `stub/chat.ts` | `?scenario=emotion` |
| `admin/ui.ts`・`store.ts` | 設定 |

## 6. 画面にキャラクターをどう出すか

いまの画面には絵が1枚も無い（`web/index.html` は文字だけ）。

- 絵は `web/public/character/<タグ>.png` に置き、**タグ名で引く**。
  絵を差し替えるのにコードを触らない
- **絵が無くても壊れない。** 見つからなければ `neutral` に落とし、
  それも無ければ何も出さない（いまと同じ画面）
- 置き場所は `stage` の中。**本文と競合させない** — 据え置きの画面は
  離れて読むので、絵で本文を狭めない
- 切り替えは CSS の `opacity` で短く挟む。**パッと切り替わると忙しない**

**絵が用意できるまでは、辞書 + 声色だけで進められる。**

## 7. 設定（`/admin`）

| 項目 | 既定 | 備考 |
|---|---|---|
| 感情タグを使う | **切**（最初は） | 切ると AI への指示ごと消える。**本文は変わらない** |
| 表情を変える | 入 | 絵が無ければ何も起きない |
| 声色を変える | **切** | 「別人になった」感を確かめてから入れる |
| 辞書で補う | 入 | タグが無い文の推定 |

**全部切れること**が肝心。タグの付きが悪かったときに、
コードを戻さず設定だけで元に戻せる。

## 8. 実装の順番

1. **辞書と表情の配管**（`ai/emotion.ts` の辞書・`emotion` イベント・画面）。
   **AI を呼ばない。** stub だけで一周する
2. **声色**（`tts.ts` の話者上書き・`queue.ts`・`protocol.ts`）。ここも stub で確かめる
3. **剥がし器とテスト**。delta の切り方を総当たりで固める。**まだ AI には指示しない**
4. **`?scenario=emotion`** を stub に足し、5種類の切り替わりを目と耳で確かめる
5. **プロンプトに指示を足す**（`/admin` で切れる形で）。**ここから実測**
6. ログを見て、タグの付き方を測る。悪ければプロンプトを直す・モデルを変える・切る

**1〜4 は課金ゼロ。** 5 の前に、感情が動く画面と声はもう完成している。

## 9. 決めたいこと

| | |
|---|---|
| 感情は5つでよいか | 増やすと絵と声の用意が増える。まず5つで足りるか使って見る |
| 声色まで変えるか | 実際に聞いて決める。まず表情だけで始める |
| `surprised` の声 | 対応するスタイルが無い。ノーマルのままか、話者を変えるか |
| 辞書をどこまで作り込むか | 凝ると外れたときに直しにくい。**「！」「ごめん」「わかりません」程度**から |
| 表情を変える単位 | いまは文ごと。回答ごとのほうが落ち着いて見えるかもしれない |
| タグをチャットに保存するか | いまは保存していない。読み返すときに要るか |
