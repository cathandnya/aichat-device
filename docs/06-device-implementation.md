# 06. デバイス側の実装案（音声は Mac に流す）

> **Mac 側は実装済み。** WebSocket `/ws`・ウェイクワードの判定・状態機械・
> リングバッファは入っている（`server/src/ws/`, `server/src/ai/wake.ts`,
> `server/src/audio/ring.ts`）。いま端末の役をしているのはブラウザ（`device/web`）。
> **残っているのはハードの選定と、端末側 150 行を書くこと**（[04](04-roadmap.md) の Phase E）。

## 前提

**サーバーは Mac に置いたまま。デバイスは端末に徹する。**

```
[デバイス]  マイク ──常時ストリーム──▶ [Mac]
            画面  ◀──状態・文字────────  ウェイクワード判定
            スピーカー ◀──音声─────────  音声認識・Gemini・VOICEVOX
```

**デバイスに機械学習は載せない。** ウェイクワードの判定も Mac 側で行う。
これが効いて、デバイスは「マイクを送る・音を鳴らす・文字を描く」だけになる。

`device/web`（ブラウザの画面）はデバイスでは使わない。Mac 上の開発・検証用に残す。

## デバイスの責務は3つだけ

```
起動時: ws://<mac>:9801/ws?device=$AICHAT_DEVICE_ID に繋ぐ
loop:
  マイクから 80ms 読む → WebSocket で送る
  受け取る: {状態, 文字} → 画面に描く
  受け取る: 音声 → 鳴らす
```

Python なら 150 行程度。判断も推論も一切しない。

> **`AICHAT_DEVICE_ID` は Mac のサーバーの設定ではない。** デバイスは
> 別の機械の別プロセスなので、Mac の `.env` は届かない。systemd ユニットの
> `Environment=` に書く。**サーバーはこの値を一度も読まない。**
>
> 名乗らないと、同じ家の他のデバイスと**会話の文脈が混ざる**
> （[07](07-chat-design.md) の「家族で共有するか」）。
> `living` `bedroom` のように、履歴の見出しで読める名前にする。
> 使えるのは英数字とハイフンで 32 文字まで。

## 音声を常時流すことの検討

### 成立する

| | |
|---|---|
| 帯域 | **256 kbps**（16kHz mono 16bit）。LAN では無視できる |
| 遅延 | LAN で 1〜5ms。80ms フレームの判定には影響しない |
| Mac の CPU | 専用モデルなら 1〜2%。連続 ASR でも 8〜12%（実測） |

### プリロールの問題が消える ★

ブラウザ版では「声を検出したと気づいた頃には語頭が過ぎている」ため、
300ms のリングバッファを常に回していた（`audio/endpoint.ts`）。

**Mac が連続バッファを持つので、検出後に手前を遡って取れる。**
デバイス側にバッファは要らない。

### 引き換えに変わること

[01-requirements](01-requirements.md) には「ウェイクワード検出は**必ずローカル**」
と書いた。これは「クラウドに出さない」という意図で、**家の外に出ない点は
変わらない**（Mac は同じ家の中）。

ただし **部屋の音が常時 LAN を流れる**。次を設計として決めておく。

| | |
|---|---|
| 経路の保護 | **平文で流さない。** TLS か共有鍵。WiFi に入れた人に聞かれる |
| Mac 側 | **音声をディスクに書かない。** 判定に使ったら捨てる |
| 無音時 | デバイス側に音量のしきい値を置き、**静かなときは送らない**。数行で済む |

## ウェイクワードをどう作るか

### 案 A: 連続 ASR + 文字列一致（**実測で成立を確認した**）

音声が Mac にあるなら、専用モデルを作らずに済む。
**Apple の音声認識（ohr）を短い窓で回し続け、書き起こしに「ねえアイチャット」が
出たら起動する。**

実測（2秒窓）:

```
1回の書き起こし  0.121秒
毎秒1回で CPU 1コアの 12%（1.5秒に1回なら 8%）
```

| 利点 | |
|---|---|
| **学習が要らない** | 一番重い作業がまるごと消える |
| **語をすぐ変えられる** | 設定の文字列を書き換えるだけ。再学習も再配布も無い |
| 精度 | 本物の ASR なので、少ない学習データのモデルより素直 |

| 欠点 | |
|---|---|
| CPU | 専用モデルの 5〜10 倍（それでも Mac なら余裕） |
| 副作用 | **部屋の会話が全部書き起こされる**（Mac 内に留まるが、事実として書いておく） |
| 誤起動 | 語が日常会話に出ると起きる。→ **実測した。下記** |

### 実測（VOICEVOX の合成音声・2秒窓を1秒ずつずらす）

**結論: 「ずんだもん」で 検出 10/10・誤起動 0/15。学習なしで成立する。**

#### 1. ウェイクワードは「綴り」ではなく「認識器が出す文字列」で決める

候補を投げて、実際に何と書き起こされるかを調べた（話者3種）。

| 候補 | 一致 | 聞こえ方 |
|---|---|---|
| ねえアイチャット | **0/3** | **恋愛チャット** |
| ねえアシスタント | 0/3 | ネイ / レイ / 名アシスタント |
| ねえロボット | 0/3 | ネイロボット / 霊ロボット |
| ねえずんだもん | 0/3 | ネズンだもん / レズンだもん |
| アイチャット | 3/3 | アイチャット |
| ハローアイチャット | 3/3 | ハロアイチャット |
| オッケーコンピューター | 3/3 | オッケコンピュタ |
| ずんだもん | 2/3 | すんだもん / ずんだもん |

**「ねえ」で始まる語は全滅。** 辞書に無い並びを実在語に寄せてしまう
（ねえアイ → 恋愛）。話者や速度を変えても一貫して同じ誤りになる。

**長音（ー）は落ちる**が一貫しているので、正規化で吸収できる。

#### 2. 「ずんだもん」の評価

危険なのは **「〜んだもん」が日常の語尾**であること。そこを狙った例を混ぜた。

| 判定語 | 検出 | 誤起動 |
|---|---|---|
| `ずんだもん` のみ | 9/10 | **0/15** |
| `ずんだもん` + `すんだもん` | **10/10** | **0/15** |

外れた1件は濁点が落ちた「すんだもん」。**許容パターンに足しても誤起動は増えなかった。**

無視できた例（すべて正しく無視）:
「だって疲れてるんだもん」「行きたくないんだもん」「もう全部済んだもん」
「前はそこに住んだもんね」「ずっと待ってるんだもん」「ずんずん進んでいく」
「ずんだ餅が食べたい」

参考: **「アイチャット」は 検出 7/10・誤起動 0/15** で、「ずんだもん」に劣った。

#### 3. 費用

1窓あたり **0.14〜0.15 秒**。1秒ごとに投げて CPU 1コアの 12〜15%。

#### 4. 実マイクで測るには

ブラウザに試験専用の画面がある。

```
https://<host>:9800/wake.html
```

**AI を呼ばない。** `/ws?mode=wake` に繋ぐと、サーバーは判定だけを行い
チャットを作らず読み上げもしない（`server/src/ws/wake-probe.ts`）。
音声認識は手元なので、**何時間流しても費用はゼロ**。

- マイクはトグルで開閉する（履歴を読むだけのときに開かない）
- 窓ごとの**聞こえ方が全部出る**。当たらなかった窓も出るので、語を選び直す材料になる
- **判定語をその場で差し替えられる。** 設定（`/admin`）は書き換えないので、
  同じ部屋の音に対して「ずんだもん」と「アイチャット」を比べられる
- 起動回数・経過時間・1時間あたりの換算が出る。ログを保存できる

> **Firefox では使えない。** `AudioContext({sampleRate:16000})` を無視するため。
> 本番の経路は WAV ヘッダに実測値を書いて逃げているが、こちらは生の PCM を
> 流すので誤魔化せない。画面に警告を出して繋がない。

#### 5. この結果の限界

**合成音声での計測。** 実際の発話・小声・早口・離れた位置・生活音の中では
悪化する。とくに誤起動 0 は楽観しすぎない方がよい。**実機で測り直すこと。**

#### 6. 設計として決めること

- **判定語は複数持てるようにする**（`ずんだもん` / `すんだもん`）。
  認識器の癖を後から足せる形にしておく
- **正規化してから比較する**（空白・句読点・長音・全半角を落とす）。
  SpeechAnalyzer は語の区切りに空白を入れ、長音を落とす
- **語は設定として持つ**（`/admin` から変えられるように）。
  学習が要らない利点は「すぐ変えられる」ことなので、そこを殺さない

### 案 B: 専用モデル（openWakeWord / microWakeWord）

案 A の CPU や誤起動が問題になったときの移行先。

**日本語の既製モデルは無い。** VOICEVOX で数千件合成して学習させる
（43話者・127スタイルあるので声の多様性は稼げる）。学習は Mac か Colab で行い、
デバイスには置かない — **Mac 側で動かすので、成果物の配置も差し替えも簡単。**

案 A で動かしておけば、移行しても**デバイス側の実装は一切変わらない。**

## ハードウェア — **決定: Raspberry Pi Zero 2 W + HDMI 液晶**

デバイスに機械学習が載らなくなったので、要求はかなり下がった。
そのうえで**「無理なく動く」を最優先**して選んだ。

### 部品表（概算 約12,000円）

| 部品 | 型番の例 | 概算 |
|---|---|---|
| 本体 | **Raspberry Pi Zero 2 W**（ピンヘッダ付き） | 2,500円 |
| マイク＋アンプ | **ReSpeaker 2-Mics Pi HAT** | 2,500円 |
| スピーカー | 3W 4Ω 小型（HAT の JST に挿す） | 500円 |
| 液晶 | **mini-HDMI 接続 4〜5インチ 800×480** | 4,000円 |
| microSD | 16GB | 800円 |
| 電源 | micro-USB 5V/2.5A | 800円 |
| ケース・配線 | | 1,000円 |

### なぜ Pi Zero 2 W か（費用ではなく実装量）

ESP32 のほうが安い（4,000円前後）。それでも Pi にしたのは、
**実装量が5倍ほど違う**ため。

| | Pi Zero 2 W | ESP32 |
|---|---|---|
| 言語 | **Python** | C / ESP-IDF |
| 日本語フォント | **OS に入っている** | 焼き込む（サブセット化が要る） |
| 描画 | pygame で数行 | LVGL の設定一式 |
| WebSocket | `pip install websockets` | 自前実装 |
| 音声 | ドライバ任せ | I2S・DMA を自分で組む |
| 反復 | ssh して編集 | ビルド → 書き込み |
| **実装量の目安** | **約150行** | 約1,000行＋設定 |

ブラウザ版（`device/web`）が実質の見本実装になっているので、
Python への移植はほぼ機械的に済む。ESP32 だと設計から書き直しになる。

推論が無いので 512MB でも余裕がある（whisper も VOICEVOX も Mac 側）。

### なぜマイクとアンプを1枚の HAT にするか

**Pi は I2S が1系統しかない。** マイク（INMP441 等）とアンプ（MAX98357A 等）を
別々に載せると、BCLK / LRCLK の共有で嵌まる。

ReSpeaker 2-Mics Pi HAT は**1枚で入出力を持つ**（WM8960 コーデック）ので、
その問題が最初から無い。マイクが2つあるぶん、聞き取りにもわずかに有利。

### なぜ液晶を HDMI にするか

SPI 液晶のほうが安い（3.5インチで 1,800円前後）が、**HAT が GPIO と SPI を
使うため衝突の恐れがある**。ここで詰まると原因究明に時間を取られる。

HDMI なら GPIO を一切使わないので、音声と表示が独立する。
書き換え速度も SPI（数 fps）より速く、流れる文字が読める。

> **Pi Zero 2 W に DSI コネクタは無い。** 公式タッチディスプレイは使えない。
> 接続は mini-HDMI か SPI/GPIO の二択。

### 採らなかったもの

| | 理由 |
|---|---|
| ESP32-S3 | 4,000円で済むが実装量が5倍。手元に余っていたが、それでも見送った |
| ESP32（WROOM-32・PSRAM なし） | 上記に加えて**音声の切り分けが必須**（下記）。SRAM 520KB では1文ぶんの音声を受け取れない |
| Raspberry Pi 4 + 公式7インチ | 3万円超。Chromium を載せないので、この性能は要らない |
| SPI 液晶 | 安いが HAT と衝突しうる。書き換えも遅い |

## 先に直すこと: 音声を小さく刻んで送る ★

**いまサーバーは1文ぶんの WAV を WebSocket の1メッセージで送っている。**
実測（VOICEVOX・速さ130%）:

| | 音声 | 1メッセージ |
|---|---|---|
| 「はい？」 | 0.6秒 | 28 KB |
| 普通の1文（20字） | 2.7秒 | **127 KB** |
| やや長い1文（42字） | 6.5秒 | **305 KB** |
| 長い1文（74字） | 10.5秒 | **494 KB** |

Pi Zero 2 W（512MB）なら受け取れるので**動かないわけではない**。
それでも直す価値がある。

- **鳴り始めが速くなる。** 全部届くのを待たずに再生を始められる
- デバイスのメモリ使用量が**一定**になる（数KBのリングバッファで足りる）
- WAV ヘッダの解析が要らなくなる
- 将来 ESP32 に移す道が残る（あちらでは必須）

20〜40ms ごとの生 PCM（16bit・VOICEVOX の 24kHz のまま）を流す形にする。
**ハードが届く前に着手できる**（ブラウザ側も同じ経路なので、そこで確かめられる）。

## ソフトウェア（Pi の場合）

**Raspberry Pi OS Lite（64bit）。デスクトップもコンポジタも入れない。**

| 層 | 選定 | 理由 |
|---|---|---|
| 描画 | **pygame（SDL2 の KMSDRM 出力）** | X も Wayland も要らず、フレームバッファに直接描く。HDMI なので解像度もそのまま出る |
| フォント | OS の Noto Sans CJK JP | 焼き込みも subset 化も要らない |
| 音声入出力 | `sounddevice`（PortAudio） | 録音と再生が同じ API |
| 通信 | `websockets` | 音声の送出と、状態・音声の受信を1本で |
| 常駐 | systemd 1ユニット | **プロセスは1つ。** `Environment=AICHAT_DEVICE_ID=living` をここに書く |

推論ライブラリが要らないので、依存は4つで済む。

## エコーキャンセル

ブラウザの `echoCancellation` に頼れなくなる。常時マイクが開くので、
**デバイスが自分の読み上げで起動し続ける**危険がある。

対策は上から順に:

1. **読み上げ中はウェイクワードの判定を止める**（Mac 側で数行）。
   一番簡単で確実。**実装済み**（`ws/session.ts`）。
   引き換えに読み上げ中の割り込みができない
2. ソフトで AEC（`speexdsp` / PipeWire のエコーキャンセル）。
   ReSpeaker のマイクとスピーカーが同じコーデック（WM8960）に載るので、
   参照信号は取りやすい
3. スピーカーを離す・音量を下げる

**まず 1 でよい。** Mac 側の状態機械が読み上げ中を知っているので、
そこで判定を止めるだけ。割り込みが欲しくなったら 2 に進む。

> **ReSpeaker 2-Mics Pi HAT にハードウェア AEC は無い。** マイクが2つあるのは
> ビームフォーミングのためで、エコーキャンセルは別の話。実機で必ず確かめること。

## Mac 側に要る変更

| 変更 | 中身 |
|---|---|
| **WebSocket の口** | 音声を受け、状態・文字・音声を返す。`/ws` |
| **ウェイクワードの判定** | 連続 ASR + 文字列一致。読み上げ中は止める |
| **連続バッファ** | 直近数秒を保持。検出時に手前を遡る |
| 状態機械をサーバーへ | いま `web/src/main.ts` にある 5 状態を移す |
| `HOST` を LAN に開く | デバイスから届くように |
| **`/api/*` に認証** | 開く以上、無認証では課金を他人に使われる |
| **スリープさせない** | `caffeinate -dims`。寝るとデバイスが死ぬ |

HTTPS は要らなくなる（デバイスは `getUserMedia` を使わないので
secure context の制約が消える）。ただし**音声を流す経路は保護すること。**

## いまの実装から移すもの

**移す先が Mac 側になったので、TypeScript のまま使えるものが増えた。**

**移し終わったものは、ブラウザ側から消した。**「ボタンを押して話す」経路を
残したままにすると同じ処理が2箇所に居座り、実機で困ることにも気づけない。

| いまの実装 | 移す先 | 状況 |
|---|---|---|
| `web/src/speech/sentences.ts` | Mac のサーバー（TS のまま） | **済み**（`server/src/speech/sentences.ts`）。ブラウザ側は削除 |
| `web/src/speech/speaker.ts` | Mac のサーバー（TS のまま） | **済み**（`server/src/speech/queue.ts`）。ブラウザ側は削除 |
| `web/src/main.ts` の状態機械 | Mac のサーバー（TS のまま） | **済み**（`server/src/ws/session.ts`）。6状態の遷移 |
| `web/src/api/client.ts` | サーバー内部の呼び出しになる | **済み**。SSE の解析はブラウザから消えた |
| `web/src/audio/endpoint.ts` | Mac 側（TS） | **済み**。プリロールは持たず、判定だけ残した |
| `web/src/audio/wav.ts` | Mac 側（TS） | **済み**（`server/src/audio/format.ts`）。ブラウザ側は録音に残る |
| `web/src/styles.css` | デバイス側の描画 | 配色（常に暗い）と文字の大きさは踏襲 |

**デバイス側に移植するのは描画だけ。** 判断のロジックは全部 Mac に残る。

## 進め方

1. ~~WebSocket の口と状態機械を Mac 側に作る~~ **済み**（`ws/session.ts`）
2. ~~ブラウザからウェイクワードを試せるようにする~~ **済み**
   （`/wake.html` と、チャット画面のマイクのトグル）
3. **実マイクで誤起動と検出率を測る** ← **いまここ**。
   `/wake.html` を開いて放置するだけ。ハード不要
4. **音声を小さく刻んで送るようにする**（上記）。ハード不要
5. 部品を買う（部品表のとおり）
6. OS を入れ、ReSpeaker の設定を通し、音が録れる・鳴ることを確かめる
7. デバイス側（150 行）を書く
8. キオスク化・自動起動（systemd 1ユニット）

**3 と 4 はハードが届く前にできる。**

## 未確定・測るべきこと

ハードが決まったので、残るのは実機でしか分からないものだけ。

| | |
|---|---|
| **誤起動の頻度** | 日常会話・テレビの音でどれだけ起きるか。`/wake.html` で測れる（ハード不要） |
| **検出率** | 小声・早口・離れた位置 |
| **エコーキャンセル** | 読み上げ中に自分の声を拾わないか。**AEC は無いので実機で必ず確認** |
| 遠距離の聞き取り | 2〜3m 離れたときの認識率。ReSpeaker の2マイクでどこまで持つか |
| Zero 2 W の描画速度 | HDMI なので問題ない見込みだが、pygame + KMSDRM の実測は取る |
| 512MB で足りるか | 推論が無いので余裕のはず。実測する |
