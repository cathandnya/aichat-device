# 06. デバイス側の実装案（Web UI を使わない）

## 前提

**サーバーは Mac に置いたまま。** デバイスは端末に徹する。

```
[Mac]  ローカルサーバー + Gemini + 音声認識 + VOICEVOX
   ↑  LAN（HTTP）
[デバイス]  画面 + マイク + スピーカー + ウェイクワード
```

whisper も VOICEVOX も Node もデバイスに載らない。**メモリは制約でなくなる。**
判断軸は「安さ・起動の速さ・ウェイクワードの実装しやすさ」になる。

`device/web`（ブラウザの画面）はデバイスでは使わない。Mac 上の開発・検証用として残す。

## デバイスの責務は4つだけ

1. ウェイクワードを常時待ち受ける
2. 起きたら話し終わりまで録る（VAD）
3. Mac に投げる（`/api/stt` → `/api/chat` → `/api/tts`）
4. 画面に出す・音を鳴らす

HTTP を3回叩いて、画面に文字を出すだけ。**ロジックはほぼ Mac 側にある。**

## ハードウェア

### 本命: Raspberry Pi Zero 2 W

| 部品 | 概算 | 備考 |
|---|---|---|
| Raspberry Pi Zero 2 W | 2,000円 | 512MB。ファンレス・静か |
| 5インチ HDMI 液晶 | 3,000〜4,000円 | Zero 2 W に DSI は無い。HDMI か SPI |
| I2S MEMS マイク（INMP441 等） | 500円 | USB ポートを塞がない |
| I2S アンプ（MAX98357A）+ スピーカー | 1,000円 | 同上 |
| microSD 16GB・電源・ケース | 2,000円 | |
| **合計** | **9,000円前後** | |

Chromium を捨てたので Pi 5 は要らない。**8GB のメモリも 27W の電源も不要。**

**懸念**: 512MB で Python + 推論ランタイムが動くか。見積もりでは
OS Lite 100MB + Python 40MB + tflite 30MB + 描画 20MB ≒ 200MB で収まるが、
**実機で確かめること。** 足りなければ Pi 4（2GB）に上げる。

**SPI 液晶にする場合の注意**: 書き換えが数 fps しか出ない。
回答が流れる表示は 2〜3 fps に間引く必要がある。時計と文字だけなら許容範囲。

### 対案: ESP32-S3（もっと安く・もっと軽く）

| | |
|---|---|
| 費用 | 3,000〜5,000円（自作）/ 10,000円（ESP32-S3-BOX-3） |
| 起動 | 1秒未満。OS が無い |
| 消費電力 | 1W 前後 |
| ウェイクワード | **microWakeWord が本来の想定環境**（Home Assistant の音声サテライトが実績） |

**この構成なら十分成立する。** 以前 ESP32 を見送ったのは
「Home Assistant が母艦として必要」という理由だったが、
**母艦は Mac なのでその前提は消えた。**

引き換えに:
- 画面が小さい（2.4〜4.3インチ）。日本語フォントは焼き込み（16px で 200KB 程度）
- 開発が C / ESP-IDF になる。Python の 5 倍は手間がかかる見込み
- 自己署名の HTTPS が扱いにくい。LAN 内の平文 HTTP に落とすことになる

**「とにかく安く小さく」を最優先するならこちら。** ただし作業量は跳ね上がる。

### 保険: Raspberry Pi 4（2GB）

Zero 2 W のメモリか処理速度が足りなかったときの逃げ先。
同じ Python のコードがそのまま動く。

## ソフトウェア（Pi の場合）

**Raspberry Pi OS Lite。デスクトップもコンポジタも入れない。**

| 層 | 選定 | 理由 |
|---|---|---|
| 描画 | **pygame（SDL2 の KMSDRM 出力）** | X も Wayland も要らず、フレームバッファに直接描く。Python で書ける |
| 音声入出力 | `sounddevice`（PortAudio） | 録音と再生を同じ API で |
| ウェイクワード | `openwakeword`（ONNX）または microWakeWord（TFLite） | 下記 |
| 発話区間 | `silero-vad` | ブラウザ版の RMS より確実 |
| 通信 | `httpx`（SSE 対応） | |
| 常駐 | systemd 1ユニット | **プロセスは1つ。**音声も描画も同居させる |

画面に出すものは「時計・状態・流れてくる文字・出典」だけなので、
GUI フレームワークは要らない。**pygame で 300 行程度。**

## ウェイクワード ★最大の作業

### 日本語の既製モデルは無い

openWakeWord にも microWakeWord にも英語のモデルしかない。**自分で学習させる。**
手順はどちらもほぼ同じで、**プラットフォームによらず同じ作業**になる。

```
VOICEVOX で「ねえアイチャット」を数千件合成
  （話者・速度・抑揚を振る。ノイズや残響を重ねる）
        ↓
学習（Mac か Colab。デバイス上ではやらない）
        ↓
成果物（.onnx か .tflite）をデバイスに置く
```

**VOICEVOX を既に持っているのが効く。** 43話者・127スタイルあるので、
声の多様性は合成だけでかなり稼げる。

### 進め方

1. まず**英語の既製モデル（`hey_jarvis`）**でデバイス側の経路を通す。
   「常時待ち受け → 起動 → 録音 → 応答」が回ることを先に確かめる
2. そのあと日本語モデルの学習に入る。ここが重い
3. 誤起動の頻度を実測する（テレビの音で起きないか）

### openWakeWord と microWakeWord

| | openWakeWord | microWakeWord |
|---|---|---|
| 形式 | ONNX | TFLite |
| 想定 | Raspberry Pi | マイコン（ESP32） |
| 大きさ | 大きい（onnxruntime が重い） | 小さい |
| Pi での動作 | 実績あり（Pi 4 で 80ms を 5ms 未満） | tflite-runtime で動く。より軽い |

**Zero 2 W なら microWakeWord（TFLite）のほうが安全。** onnxruntime は
512MB では重い。ESP32 に乗り換える可能性を残す意味でもこちら。

## エコーキャンセルが本番の課題になる

ブラウザの `echoCancellation` に頼れなくなる。常時マイクが開くので、
**デバイスが自分の読み上げで起動し続ける**危険がある。

対策は3段階。上から順に試す。

1. **読み上げ中はウェイクワードの判定を止める**（一番簡単で確実）。
   ただし読み上げ中に割り込めなくなる
2. **AEC 付きのマイクを使う**（USB 会議マイク等）。Zero 2 W では USB が
   1ポートしかないのがつらい
3. **ソフトで AEC**（`speexdsp` / PipeWire のエコーキャンセルモジュール）

**まず 1 でよい。**割り込みは後回しにできる。

## Mac 側に要る変更（少ない）

| 変更 | 理由 |
|---|---|
| `HOST` を LAN に開く | デバイスから届くようにする |
| `/api/*` に認証を足す | 開く以上、無認証では課金を他人に使われる |
| 自己署名 HTTPS をやめるか、証明書を配る | デバイスは `getUserMedia` を使わないので **HTTP で足りる**。secure context の制約が消える |
| **Mac をスリープさせない** | `caffeinate -dims`。寝るとデバイスが死ぬ |

`/api/tts` は今のまま WAV を返せばよい。デバイス側で鳴らすだけ。

## いまの実装から移すもの

TS で書いた部分は、**設計はそのまま・言語だけ Python に**。
どれもテスト付きで仕様が固まっているので機械的に移せる。

| いまの実装 | 移植先 | 備考 |
|---|---|---|
| `speech/sentences.ts` | 文の切り出し | 文末でだけ切る規則をそのまま |
| `audio/endpoint.ts` | 発話区間 | プリロール 300ms の考え方は同じ。判定は silero-vad に差し替え |
| `audio/wav.ts` | WAV 化 | `soundfile` か `wave` で済む |
| `api/client.ts` | SSE の解析 | `httpx` で |
| `speech/speaker.ts` | 再生キュー | **合成と再生を分けて先読み**する構造は必須 |
| `main.ts` | 状態機械 | 5状態の遷移をそのまま |
| `styles.css` | pygame の描画 | 配色（常に暗い）と文字の大きさは踏襲 |

## 未確定・測るべきこと

| | |
|---|---|
| Zero 2 W の 512MB で足りるか | 実機で。足りなければ Pi 4 |
| ウェイクワードの CPU 使用率 | Zero 2 W は Pi 4 の 1/3〜1/4 の速さ |
| 日本語モデルの精度と誤起動 | 学習してみないと分からない |
| SPI 液晶の書き換え速度 | 流れる文字が見られるか |
| 全体の応答遅延 | LAN のホップが増える（数 ms のはず） |
| Mac が寝る問題の運用 | `caffeinate` で足りるか |

## 判断が要る点

**ESP32-S3 にするか Pi Zero 2 W にするか。**

- 費用と消費電力と起動の速さ → ESP32
- 開発の速さと、いまの資産の移しやすさ → Pi

作業量の差が大きいので、**まず Pi Zero 2 W で作って動かし、
それでも重い・高いと感じたら ESP32 に移す**のが安全だと考える。
ウェイクワードの学習という一番重い作業は、どちらでも共通で無駄にならない。
