# 07. チャットの設計（単発から会話へ）

> **書いた時点の話。** 当時は1問1答で、会話は「直近3往復・5分」という
> 暫定の持ち方をしていた（`ws/session.ts` の `HISTORY_TURNS` / `HISTORY_TTL_MS`）。
> 保存もしていないので、あとから読み返せなかった。

これを **チャット（会話の単位）** として扱えるようにする。
**以下は実装済み**で、1章の区切りの規則はその後さらに変えている（同章）。

---

## 1. 終了判定 ★ 最初に決めること

### 「終了」には2つの意味がある

混ぜて考えると決まらない。分ける。

| | 何を指すか | 効いてくるもの |
|---|---|---|
| **A. 受付の終了** | マイクをウェイクワード待ちに戻す | 体験。「また名前を呼ばないといけないのか」 |
| **B. 文脈の終了** | 次の質問に前の話を持ち越さない | 課金・回答の精度・家族間のプライバシー |

**A は窓、B は間（ま）で決める。** 当初は「A と B を一致させる」＝
**ウェイクワードで仕切り直し**にしていたが、これは使ってみて失敗だと分かった
（次節）。いまは 2 つを別々に見ている。

| | 何で決めるか | 既定 |
|---|---|---|
| **A. 受付の終了** | 追い質問の窓が閉じたら | 無言 8 秒 |
| **B. 文脈の終了** | 前に話してから**間があいたら** | 10 分 |

### なぜ変えたか（実際の記録）

最初の実装は **ウェイクワード＝新しいチャット**だった。追い質問の窓は
8 秒しかないので、少し考えて言い直すだけで文脈が飛ぶ。
`data/chats/` に残った 7 件がそれを示していた。

```
03:51:34  1往復  「こんにちは。」
03:55:36  1往復  3.8分後   「駅までの行き方は。」
03:59:17  1往復  3.4分後   「特に用はない。」
03:59:54  2往復  0.3分後   「なんでもない。」
04:13:28  1往復  13.2分後  「今日これから雨降る。」
04:16:30  3往復  2.7分後   「東京なんだけど。」
```

**最後の2件が決定的。**「今日これから雨降る」の 2.7 分後に「東京なんだけど」と
言っているのに、別チャットなので **AI には文脈が渡っていなかった**。
7 件のうち 5 件が 1 往復で終わっており、会話がひとつも続いていない。

上の間隔（3.8 / 3.4 / 0.3 / 13.2 / 2.7 分）に 10 分を当てると、
`03:51〜03:59` と `04:13〜04:16` の 2 つにまとまる。これが狙いどおりの区切り。

### いまの規則

```
ウェイクワード          → 前に話してから 10 分以内なら、その会話の続き
                          10 分を超えていたら、新しいチャットを始める
回答の読み上げが終わる  → 追い質問の窓を開く（既定 8 秒）
窓の間に話しかける      → 同じチャットの続き。窓を開き直す
窓が無言で閉じる        → 受付だけ終わる。文脈は 10 分間そのまま残る
```

**AI に送るのは直近 5 往復だけ**（保存は全部のまま）。
会話がいくら続いても送る量が一定になるので、文脈が伸びて課金が膨らむことも、
途中で強制的に打ち切る必要もない。「古い履歴は自動で消える」の実体はこれ。

> **明示的に仕切り直す手段は無い。** ウェイクワードが文脈を捨てなくなり、
> Web UI の「新しい会話」も外した。**意図的にそうしている。**
> リセットしたいなら 10 分待つ。仕切り直す操作（長押しなど）は、
> 必要になってから考える。

### 窓を閉じる条件

| 条件 | 既定 | 理由 |
|---|---|---|
| **無言が続いた** | **8 秒** | Alexa の Follow-Up Mode が約5秒、Google の継続会話が約8秒。この辺りが相場 |
| **終了語が聞こえた** | 「ありがとう」「おわり」「もういい」「またね」 | 自然に終われる。ウェイクワードと同じ仕組み（文字列一致）で作れる |
| **往復の上限** | 50 往復 | **暴走よけ**。文脈の長さは直近5往復で絞るので、これは一覧が遅くなるのを防ぐためだけにある（50往復×200件で一覧 191ms） |
| **エラーが起きた** | — | 失敗したまま続きを聞かれても噛み合わない |

経過時間での打ち切りは**やめた**。「間があいたか」を見る役割と重なるうえ、
話している最中に会話が別のチャットへ切り替わってしまうため。

### 呼ばれただけのとき

「ずんだもん」とだけ言われて質問が続かなかったら、**効果音だけ鳴らして待つ。**

```
ウェイクワード → （質問が来ない）→ 効果音 → 追い質問の窓 → 続けて質問できる
```

- **声では返さない。** アレクサに合わせた。呼ばれるたびに喋られると、
  続けて話そうとしているところに**被る**。音が鳴れば起きたことは分かる
- **失敗にしない。** 「聞き取れませんでした」と言われるのは、こちらが悪いことに
  されているようで感じが悪い。無反応も壊れているように見える
- 返事は `/admin` で足せる（既定は空）。**入れれば読み上げる。AI は呼ばない**
- **1つのチャットで1回だけ。** 物音で silence を繰り返すたびに
  返事を続ける機械になるのを避ける

> **返事をしないときは、その場で窓を開ける。** 読み上げる経路は
> 「鳴り終わり」を合図に窓を開くが（`onSpoken`）、鳴らさないときは
> その合図が来ない。**音は鳴るのに何も聞いていない**状態になるので、
> `acknowledge()` で明示的に開けている。

**一度も話さずに終わったチャットは保存しない。** 呼びかけただけ・物音で起きただけの
ものが履歴に「（無題）」として並ぶと、読み返すときに邪魔になる。

### 窓を開けている間の危険

**窓の間は、部屋の話し声を拾って AI に投げてしまう。** これは課金に直結する。
対策を最初から入れておく。

- **窓が開いていることを画面に出す**（「続けてどうぞ」）。黙って聞かない
- **短すぎる発話は捨てる**（1〜2文字の相槌など）
- **窓の長さを `/admin` で変えられるようにする。0 秒＝毎回ウェイクワードが要る**
  を選べるようにしておく。誤爆が気になる家庭はこれで止められる
- 読み上げ中は窓を開かない（既に決めてある）

### 採らなかった案

| 案 | 理由 |
|---|---|
| AI に「会話は終わったか」を判定させる | 呼び出しが1回増え、遅くなり、外れる。判定に課金するのは筋が悪い |
| 話題の変化で切る | 予測できない。利用者が規則を覚えられない |
| 終了ボタンだけ | 声で使う機械なのに、終わるのに手が要るのは倒錯している |
| 窓を長くして常時受付 | 部屋の会話を拾い続ける。課金とプライバシーの両方で悪い |

## 2. データの持ち方

### チャット1つ

```jsonc
{
  "id": "2026-08-27T02-15-33-a1b2",
  "startedAt": "2026-08-27T02:15:33.000Z",
  "updatedAt": "2026-08-27T02:16:40.000Z",
  "origin": "device",          // device | web（どの経路か）
  "deviceId": "living",        // どの機械か。名乗らなければ unknown、
                               // 端末を分ける前の記録は空文字
  "title": "明日の天気は",       // 最初の質問から切り出す（AI は使わない）
  "endedBy": "timeout",        // timeout | phrase | wake | limit | error | manual
  "turns": [
    { "role": "user", "content": "明日の天気は", "at": "..." },
    { "role": "assistant", "content": "…", "at": "...", "sources": [...] }
  ]
}
```

**題名は最初の質問の冒頭を切り出す。** AI に付けさせると1回ぶん課金が増え、
遅くなる。読み返すのに困らない程度で足りる。

### どこに置くか

`data/chats/<id>.json`。**1チャット1ファイル。**

- 1ファイルにまとめると、書き込みのたびに全体を読み書きすることになる
- 一覧は `data/chats/index.json` に持つ（id・題名・更新時刻・往復数・origin）。
  ディレクトリを毎回舐めるより速く、壊れても本体から作り直せる

**保存の是非**: いままで何も保存していなかった。読み返せるようにする以上、
**部屋で話した内容が Mac のディスクに残る。** そのうえで、

- 保存するのは**書き起こしと回答だけ**。**音声は保存しない**
- **保存件数に上限**を設ける（既定 200 件）。古いものから消す
- Web UI から**1件ずつ消せる**ようにする
- `data/` は `.gitignore` 済み。ファイルの権限は 0600

### 家族で共有するか

**見える範囲と、続きになる範囲は別。**

| | どうするか | なぜ |
|---|---|---|
| **文脈（続く）** | **端末ごとに分ける** | 居間の会話を寝室のデバイスが引き取ると、寝室の質問に居間の文脈が付いて AI に渡る |
| **履歴（読む）** | **画面からはその端末のぶんだけ**（`/history`） | 居間のデバイスで寝室の会話を読み返す場面が思いつかない。端末を分ける前の記録まで並ぶと邪魔になる |
| | **家じゅうは管理画面から**（`/history?all=1`） | 「さっき子どもが何を聞いたか」を見返す入口は残す |

管理画面の入口は**既存の履歴の画面に `?all=1` で入るだけ**にした。
同じものを2つ作ると、片方だけ直して食い違う。

据え置きが1台のうちは同じことだが、2台置いた瞬間に分かれる。
`findResumable` の絞り込みは `origin`（device / web）ではなく
**`deviceId`（どの機械か）**で行う。

#### 見分け方

**端末が自分で名乗る。** `/ws?device=<id>` にクエリで載せる。

| 案 | 判定 |
|---|---|
| **端末が名乗る id** | **採用。** ブラウザは `localStorage` に `browser-a3f9` を作る。実機は `AICHAT_DEVICE_ID=living` |
| MAC アドレス | **使えない。** TCP では届かない（同じ L2 で ARP を引く必要がある） |
| IP アドレス | **弱い。** 開発中は Vite のプロキシ経由なので全部 `127.0.0.1` に潰れる。DHCP で変われば会話が切れ、同じ機械の2つのブラウザは同じ扱いになる |

id は3種類に分かれる。**空文字と `unknown` を混ぜないのが肝。**

| 値 | 意味 | 継ぐか |
|---|---|---|
| `""` | 端末を分ける前に保存された記録 | **継がない**（今の端末が身に覚えのない会話を引き取らない） |
| `unknown` | 名乗らなかった端末（古いクライアント・素の接続） | 名乗らない者どうしでは継ぐ（従来どおり） |
| `living` / `browser-a3f9` | 名乗った端末 | 同じ id とだけ継ぐ |

`?all=1` の履歴は**端末ごとの見出しでまとめる**。1台ぶんしか出さないときは
見出しを立てない（同じ名前が1つ並ぶだけになる）。

## 3. API

| メソッド | パス | 中身 |
|---|---|---|
| `GET` | `/api/chats` | 一覧（id・題名・更新時刻・往復数・origin・deviceId）。新しい順。**`?device=<id>` でその端末のぶんだけ**（既定は全部） |
| `GET` | `/api/chats/:id` | 1件の全文 |
| `POST` | `/api/chats` | 新規チャットを作り、id を返す |
| `DELETE` | `/api/chats/:id` | 消す |
| `POST` | `/api/chat` | **`chatId` を受けるようにする。** 無ければ新規に作る |

WebSocket は `/ws?device=<id>`。**検証はここ1箇所だけ**で行い、通った値は
「保存してよい・画面に出してよい・ファイル名に入れてよい」ものとして下流へ渡す
（`[A-Za-z0-9][A-Za-z0-9-]{0,31}`。先頭のハイフンは弾く）。
名乗らなければ `unknown`。`?mode=wake` はチャットを作らないので要らない。

`/api/chat` は互換を保つ。`chatId` が無ければ「1回きりのチャット」として
新規に作って返す。既存の呼び出しが壊れない。

## 4. Web UI

**画面を2つに分けた。チャットと履歴を同居させない。**

当初は左に履歴、右に本文の1画面だったが、これは実機（Pi + 液晶）に
存在しない形だった。手元のブラウザで具合を見ても、実機で困ることに
気づけない。**チャットの画面は実機に寄せる。**

### `/` — チャット

```
┌────────────────────────────────────────────┐
│ 09:54                                 履歴 │
│                                            │
│ 聞いています                                 │  ← 縁が光る
│ ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  │  ← 声の大きさ
│ 「明日の天気は」                              │
│ 明日の東京は晴れ時々…                         │
│                                            │
│                 マイク ON                    │
└────────────────────────────────────────────┘
```

- **いまの会話だけ。** 過去のチャットは出さない
- **ボタンは実機に無いものを置かない。** 「話す」も「新しい会話」も外した。
  残るのはマイクの入り切りだけ（下の中央）。読み返す出口は右上に離す
- 話しかけるのはウェイクワード。会話の区切りは**間があいたか**で決まる

#### 声を受け付けていることを、離れていても分かるように

「聞いています」の文字色が変わるだけでは、部屋の向こうからは気づけない。
`listening` と `following` の間は 3 つ同時に変える。

| | 何を | なぜ |
|---|---|---|
| **画面の縁が光る** | listening は青、following は緑。ゆっくり明滅する | 文字が読めない距離でも分かる |
| **状態の文字が大きくなる** | 1rem → 2rem | 近づけば何をしているか読める |
| **声の大きさが動く** | マイクの実測値をそのまま | **届いていることの証。** 「聞いています」と出ていても、マイクが別の機器を向いていれば届いていない |

#### ウェイクワードに気づいたら音を鳴らす

`resource/wake.mp3`（`device/web/public/wake.mp3`）。呼んでから聞き取りが
始まるまで無反応だと、**呼んだ人はもう一度呼んでしまう。**

サーバーは `startChat()` で `{ type: "wake" }` を送る。**状態の遷移では
代わりにならない**（追い質問の窓から呼び直したときも `listening` に入るので、
どちらでウェイクワードが効いたのか区別できない）。

### `/history` — 履歴

```
┌──────────────┬────────────────────────────┐
│ ← チャットに戻る │ 履歴                8 件    │
│ 🎙 明日の天気は  │ 明日の天気は  09:54・…  消す │
│    09:54・4発言  │ 質問 明日の天気は            │
│ 🎙 晩ごはんの相談 │ 回答 明日の東京は晴れ時々…    │
│    09:31・6発言  │                            │
└──────────────┴────────────────────────────┘
```

- **読むだけ。ここでは話せない。** マイクも読み上げも読み込まない
- 1件ずつ**消せる**（家族の会話が入るので、**2回押させる**）
- 🎙 が付いているのはデバイスで話したもの

以前は「過去のチャットを開いたら続きを話せる」ようにしていたが、やめた。
続きは**間があいたかどうか**で決まるようになり（1章）、古い会話を掘り起こして
続ける操作は実機に無い。

### デバイスの画面はどうするか

**履歴は出さない。** デバイスは話すための機械で、読み返すのは Web UI の役割。
画面が小さく、操作もしづらい。

ただし**いまのチャットの往復は出す**（前の質問と回答が見えたほうが会話として自然）。

## 5. デバイスの挙動

```
待機 ──ウェイクワード──▶ 10分以内の会話があれば継ぐ ──▶ 聞き取り ──▶ 回答
                          （無ければ新規チャット作成）
                                                      │
                          ┌───────────────────────────┘
                          ▼
                    追い質問の窓（8秒）
                      │        │
              話しかけた    無言／終了語／上限
                      │        │
                      ▼        ▼
                   同じチャット  受付終了 → 待機（文脈は10分残る）
```

**画面に出す状態が1つ増える**: `following`（追い質問の窓が開いている）。
「続けてどうぞ」と出す。黙って聞いている状態を作らない。

## 6. 設定（`/admin`）

| 項目 | 既定 | 備考 |
|---|---|---|
| 追い質問の窓 | 8 秒 | **0 なら毎回ウェイクワードが要る** |
| 終了語 | ありがとう / おわり / もういい / またね | ウェイクワードと同じ仕組み |
| 呼ばれたときの返事 | **空**（効果音だけ） | 入れれば読み上げる。AI は呼ばない |
| **次の会話とみなす間** | **10 分** | これ以上あいたら仕切り直す。0 なら毎回まっさら |
| **AI に渡す往復数** | **5 往復** | 保存は全部のまま、送る分だけ絞る。増やすほど課金が増える |
| 往復の上限 | 50 | 暴走よけ。一覧の速さのため |
| 保存件数の上限 | 200 | 古いものから消す |

---

## 7. 実装の順番

1. **保存の仕組み**（`data/chats/`・一覧・上限・削除）
2. **API**（`/api/chats` 一式、`/api/chat` に `chatId`）
3. **Web UI**（履歴・新規チャット・削除）
4. **セッションをチャット単位に**（`ws/session.ts`。追い質問の窓と終了判定）
5. `/admin` に設定を足す

**1〜3 はデバイスと無関係に進められる。** 先に Web UI で会話として
成立させてから、デバイス側の窓を作るのが安全。

## 8. 決めたいこと

| | |
|---|---|
| 追い質問の窓は 8 秒でよいか | 短いと不便、長いと誤爆。実際に使って調整 |
| 終了語をどうするか | 「ありがとう」は会話の途中でも出る。誤終了が起きうる |
| 過去のチャットの続きを、**デバイスから**始められるようにするか | いまは Web UI だけの想定。要るなら仕組みが増える |
| 家族ごとに分けるか | いまは共有前提。分けるなら誰が話したかの判別が要る |
